Impersonation lets a platform administrator open a short-lived session as a
customer to reproduce an issue or inspect what that customer sees. It is
deliberately narrow: one organization per session, no refresh token, no account
or security changes, and sensitive permissions such as billing stay closed.

## Enable it

Impersonation is off by default:

```go
cfg := config.Default()
cfg.CoreAuth.ImpersonationEnabled = true
cfg.CoreAuth.ImpersonationMaxDuration = 15 * time.Minute // default; the hard cap
```

The admin plugin and the organizations plugin must both be registered. The
endpoint is mounted under the admin prefix:

```
POST /auth/admin/users/{id}/impersonate
```

```json
{
  "organizationId": "org_abc123",
  "duration": "10m"
}
```

The response contains the target user, the session, a bearer `token`, and the
impersonation record. The administrator's own session is untouched: store the
token separately and use it as `Authorization: Bearer <token>` for the
impersonated view. To stop, call the normal logout endpoint with that token.

## Limits

| Limit | Behavior |
|-------|----------|
| Actor | Admin-plugin `admin` role only; organization roles cannot start impersonation |
| Scope | Exactly one organization; requests for any other organization are denied |
| Lifetime | Capped by `ImpersonationMaxDuration` (15 minutes by default) |
| Refresh | No refresh token; the session cannot be extended |
| Nesting | An impersonation session cannot start another impersonation |
| Account security | Password, email, OTP, MFA, OAuth-link, session-management, and admin routes are blocked |
| Destructive | Organization deletion is always denied during impersonation |
| Revocation | Disabling or demoting the administrator deletes the sessions they started |
| Audit | `impersonation_started`, `impersonation_ended`, and `impersonation_denied` events |

The session inherits the target's normal organization role, so ordinary
organization operations are available. Account-level and security-level routes
are blocked by `core.DenyImpersonated`, even when the target is an owner or
administrator.

## Sensitive permissions

Billing and similar features are app-defined. Register them in the permission
catalog and mark them `Sensitive`:

```go
orgPlugin := organizations.New(&organizations.Config{
    Permissions: map[organizations.Permission]organizations.PermissionDefinition{
        "billing:manage": {
            Module:      "billing",
            Description: "Change plan, payment method, and invoices",
            Sensitive:   true,
        },
    },
    // Optional explicit deny list for permissions absent from the catalog.
    ImpersonationDeniedPermissions: []organizations.Permission{"billing:export"},
}, store, plugins.DialectPostgres)
```

Then protect the billing routes with the sensitive check:

```go
orgGroup.GET("/organizations/:id/billing",
    requireAuth(orgPlugin.RequireOrgSensitivePermission("billing:manage")(handler)),
)
```

`RequireOrgSensitivePermission` refuses impersonation sessions even if the
target's role carries the permission. `HasOrgSensitivePermission` is the
programmatic equivalent.

## Editing sensitive settings

Sensitive permissions are owner-only. The regular member-permissions endpoint
refuses sensitive entries for non-owners, role definitions containing sensitive
permissions can only be created or updated by the owner, and assigning such a
role is owner-only. A dedicated endpoint makes the separation explicit:

```
PUT /organizations/{id}/members/{userId}/sensitive-permissions
```

It accepts the same body as the regular permissions endpoint but only for
permissions marked sensitive, requires an owner session, and rejects
impersonation outright. The owner's own overrides cannot be changed.

:::note
Aegis stores authorization, not billing data. The billing service must also
enforce the impersonation boundary: pass the request context to
`HasOrgSensitivePermission` or gate the route with `RequireOrgSensitivePermission`
rather than checking only the target's role.
:::
